# 동고리 현행 기능 정의서

> 기준: `codex/donggori-hardening`
> 운영 형태: Next.js on Vercel + PostgreSQL/Supabase
> 이 문서는 “새 프로젝트 제안서”가 아니라 현재 코드와 운영 의도를 설명한다.

## 1. 서비스 목적

동고리는 의류 제작을 원하는 사용자가 봉제공장을 탐색하고 조건에 맞는 공장을 추천받아 문의할 수 있게 한다. 공장은 동고리 운영자가 직접 등록·관리한다. 상담과 작업지시서 전달은 동고리 공식 카카오 오픈채팅에서 이어진다.

## 2. 사용자 역할

### 방문자

- 메인, 서비스 안내, FAQ, 약관, 활성 공지·팝업 열람
- 개인정보를 제외한 공장 목록·상세 열람
- 조건 기반 맞춤 추천 실행
- 문의 저장 단계에서는 로그인 안내

### 일반 사용자

- 이메일/비밀번호 또는 카카오·네이버 계정으로 로그인
- 공장 문의 등록 및 본인 문의 내역 열람
- 이름·휴대폰 번호 등 본인 프로필 수정
- 문의 완료 후 공식 카카오 오픈채팅으로 이동

### 관리자

- 별도 서명된 관리자 세션으로 관리자 화면과 API 사용
- 공장, 공장 이미지, 공지, 팝업 등록·수정·삭제
- 운영 통계 및 문의/추천 피드백 확인

공장 전용 계정, 공장 로그인, 공장 대시보드, 공장 직접 정보 수정은 지원하지 않는다.

## 3. 인증

- 브라우저가 신뢰하는 인증 정보는 HttpOnly `access_token` 쿠키 하나다.
- UI 인증 상태와 사용자 프로필은 `GET /api/auth/me` 응답을 기준으로 한다.
- `localStorage`, JavaScript로 읽을 수 있는 사용자 JSON 쿠키, `isLoggedIn` 플래그는 인증 근거로 사용하지 않는다.
- 이메일 회원가입과 비밀번호 재설정은 서버가 발급한 이메일 인증 증명을 요구한다.
- 카카오·네이버 OAuth는 서버가 생성한 state와 쿠키를 검증한다.
- 같은 이메일이 이미 있어도 서로 다른 소셜 계정을 자동으로 덮어쓰거나 연결하지 않는다. 기존 로그인 방식으로 인증한 뒤 명시적으로 연결하는 기능을 만들기 전까지는 안내 오류를 반환한다.
- 로그인 전 접근한 내부 경로는 검증된 같은 사이트 상대 경로만 `next`로 보존한다. 외부 URL과 `//host` 형태는 거부한다.

## 4. 공장 정보

- 원본은 Supabase `donggori` 테이블에 보관한다.
- 브라우저는 Supabase 테이블을 직접 조회하지 않고 `GET /api/factories`, `GET /api/factories/[id]`를 사용한다.
- 공개 API는 표시용 필드만 화이트리스트로 반환한다. 담당자명, 전화번호, 이메일, 개별 카카오 URL 등 직접 연락 가능한 필드는 공개하지 않는다.
- 대표·추가 이미지는 DB의 `image`, `images` 값을 기준으로 한다.
- 좌표가 없는 공장은 임의 좌표로 대체하지 않으며 지도 표시 대상에서 제외한다.

## 5. 맞춤 추천

- 현재 추천은 생성형 AI가 아니라 사용자가 선택한 지역·품목·원단·수량 등의 조건을 비교하는 규칙 기반 점수다.
- 선택하지 않은 조건과 공장 데이터가 없는 조건을 임의의 성공 점수로 계산하지 않는다.
- 동점은 안정적인 기준으로 정렬하며 요청할 때마다 무작위 결과를 만들지 않는다.
- 일치 조건이 없는 결과를 100점으로 표시하거나 특정 공장을 강제로 1위에 두지 않는다.
- 화면과 메타데이터에서는 “AI 매칭” 대신 “맞춤 추천”을 사용한다.

## 6. 문의

- 로그인 사용자는 `POST /api/match-requests`로 문의를 저장한다.
- 서버는 쿠키 세션에서 사용자 ID·이메일을 가져오며, 요청 본문의 사용자 식별자를 신뢰하지 않는다.
- 서버는 공장 ID로 실제 공장 존재 여부와 표시 이름을 확인한다.
- 사용자는 본인 문의만 조회할 수 있고 관리자는 전체를 조회할 수 있다.
- 공장 역할의 조회·상태 변경·알림톡/SMS 전송 API는 제공하지 않는다.
- 민감한 작업지시서 파일은 public Supabase Storage에 올리지 않는다. 사용자는 문의를 저장한 뒤 공식 오픈채팅에서 파일을 전달한다.

## 7. 공지와 팝업

- 공개 목록·상세는 `is_active=true`이고 현재 시각이 노출 기간 안인 항목만 반환한다.
- 공개 API는 화면에 필요한 필드만 반환한다.
- 조회 요청은 중복 행 삭제나 시드 생성 같은 DB 변경을 일으키지 않는다.
- 생성·수정·삭제는 관리자 세션이 필요한 별도 API에서만 수행한다.

## 8. 데이터 접근과 보안

- Vercel 서버 API만 `SUPABASE_SERVICE_ROLE_KEY`를 사용한다.
- 브라우저의 `anon`, `authenticated` 역할은 애플리케이션 테이블을 직접 읽거나 쓰지 못한다.
- 사용자, 세션, OTP, 문의, 공장, 공지, 팝업 등 대상 테이블은 RLS를 활성화하고 브라우저 역할의 table 권한과 공개 정책을 제거한다.
- 서버 API는 입력 길이·형식·URL·파일 MIME/크기를 검증하고 응답 필드를 제한한다.
- 세션·관리자 쿠키는 HttpOnly, Secure(운영), SameSite=Lax로 설정한다.
- 비밀키와 service role 키는 저장소나 `NEXT_PUBLIC_*` 환경변수에 두지 않는다.

## 9. 배포

- 패키지 관리자는 npm과 `package-lock.json`을 기준으로 한다.
- 기본 검증은 보안 회귀 테스트, TypeScript, ESLint, Next.js production build 순서로 실행한다.
- Vercel Preview에서 핵심 흐름을 확인한 뒤 Production을 배포한다.
- Supabase 차단 마이그레이션은 서버 API 전환 코드가 Production에 반영된 뒤 실행한다.
- 상세 운영 순서는 `docs/hardening/database-and-deployment.md`를 따른다.

## 10. 지원하지 않는 기능

- 공장 회원가입·로그인·대시보드
- 공장별 직접 카카오 링크 공개
- 공장에 알림톡/SMS 자동 발송
- 웹에서 민감한 작업지시서 public 업로드
- 사용자가 직접 공장 정보를 수정하는 기능
- 근거 없는 “AI”, “인증된 70+”, “지역 TOP 100” 등의 홍보성 자동 문구

이 기능이 다시 필요해지면 기존 레거시 코드를 되살리지 않고 사용자 권한, 개인정보 보존기간, 파일 접근 통제, 운영 책임자를 먼저 정의한 새 기능으로 설계한다.
